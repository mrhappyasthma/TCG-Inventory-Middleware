# Project Guidelines & Rules: TCG Card Inventory Middleware

## 1. 🔄 Git Commit & Push Workflow (Mandatory Rule)

* **Remote**: [`github.com/mrhappyasthma/TCG-Inventory-Middleware`](https://github.com/mrhappyasthma/TCG-Inventory-Middleware) (`origin`, branch `main`).

* **Commit Every Change**: Always create a clean git commit after completing each feature implementation, bug fix, refactoring, or configuration update.
* **Verify Before Committing**: Always run the automated test suites before committing to ensure no regressions:
  ```powershell
  python -m unittest discover -s tcg_engine/tests
  python -m unittest discover -s ebay_client/tests -t ebay_client
  python -m unittest discover -s tests
  ```
  The `-t ebay_client` is required, not cosmetic: run from the project root
  without it, the outer `ebay_client/` directory shadows the installed package
  as an empty namespace package and every import of its public API fails.
* **The suite checks the JavaScript.** `tests/jslint.py` is a lexical validator for `app/static/app.js`: it tokenises strings, template literals with `${}` nesting, comments and regex literals, then asserts every literal is closed and brackets balance. It exists because a string containing a real newline instead of a backslash-n escape shipped, and a syntax error anywhere in `app.js` stops the *whole file* executing -- the page rendered as signed out and the sign-in button did nothing, because no handler had been bound. Verifying element ids and handler names, which is what was being done, cannot catch that. **Never hand-write code containing backslash escapes through a shell heredoc**, in any language: that is what mangled the escape. The rule was written for JavaScript and then cost three attempts on a Python patch, where a heredoc collapsed every doubled backslash -- turning a regex backreference into a literal 0x01 byte and a newline escape into a real newline inside an f-string. Use the file-editing tools for such edits, or restructure the code to need no escapes at all: the regex that provoked it was replaced with a rpartition and a replace, which is clearer anyway. If `node` is on PATH the suite also runs `node --check`, which is a real parser and strictly better; installing it upgrades the check with no code change.
* **Conventional Commit Format**: Use clear, descriptive commit messages following conventional commits:
  * `feat: <summary>` for new features or enhancements
  * `fix: <summary>` for bug fixes
  * `refactor: <summary>` for code restructuring or cleanup
  * `test: <summary>` for test additions or updates
  * `docs: <summary>` for documentation or guideline changes
  * `chore: <summary>` for configuration, Docker, or dependency adjustments
* **Push Immediately After Committing**: Run `git push origin main` as soon as each commit is created. Do not batch commits up locally and do not wait to be asked — the NAS deploys via `git pull origin main`, so an unpushed commit cannot be deployed.
* **Sole Attribution**: Commits are attributed to the repository owner only. Do **not** append a `Co-Authored-By:` trailer (for Claude or any other tool) to commit messages. Message quality is unchanged — conventional prefix, subject line, and a body explaining *why* — only the trailer is omitted.
* **Atomic & Reversible**: Keep commits logical and granular so that changes can be easily tracked, reviewed, or rolled back if needed.
* **History is Append-Only Once Pushed**: The standing push permission covers ordinary commits to `main` only. Force-pushing, rewriting or rebasing pushed commits, creating tags or releases, and deleting branches all require asking first.
* **Never Commit Secrets**: `.env`, `data/*.db` and `data/.session_secret` are gitignored and must stay that way. `.env.example` carries empty placeholders only — never a real `GOOGLE_CLIENT_ID` or `JWT_SECRET`.

## 2. 🐳 Synology NAS Deployment & Environment Constraints

* **Deployment Target**: Synology NAS via Docker / Container Manager (`docker-compose.yml`).
* **Persistent Storage**: All persistent database storage must be mapped to `/data` in container and volume mounted to host.
* **Separation of Concerns**: three components, and the boundaries are load-bearing.
  * Core engine in [`tcg_engine/`](file:///c:/Users/Mark/Documents/GitHub/SoftSwift-Ebay-CSV-Converter/tcg_engine) MUST remain pure Python with zero web dependencies so it can be extracted to its own repo or executed via CLI.
  * eBay API interaction lives in [`ebay_client/`](file:///c:/Users/Mark/Documents/GitHub/SoftSwift-Ebay-CSV-Converter/ebay_client), its own package with its own tests. Never put HTTP calls to eBay inside an `app/main.py` endpoint, and never grow them inside `tcg_engine`. The boundary is a *vocabulary* boundary: the client speaks SKUs, offers, inventory item groups and order line items, and knows nothing about manifest IDs, pricing rules or SortSwift. Translation happens in the layer above so neither model leaks into the other. It is also the only component holding remote credentials, quotas, retries and signed callbacks, and keeping that behind one seam is what makes it testable with no network access.
  * Web backend in [`app/`](file:///c:/Users/Mark/Documents/GitHub/SoftSwift-Ebay-CSV-Converter/app) imports both. **Import submodules, not the package root** (`from ebay_client.config import EbayConfig`, not `from ebay_client import EbayConfig`): the app puts the project root on `sys.path`, where the outer `tcg_engine/` and `ebay_client/` directories shadow the installed packages as empty namespace packages. A submodule import resolves through the editable-install finder anyway; a package-root import returns an object with no attributes.
* **Platform Compatibility**: Code is developed on Windows and deployed to Linux (Synology DSM). Path handling must use `os.path` and avoid OS-specific hardcoding. Explicitly close SQLite connections to prevent Windows file locking.

## 3. 🏷️ Business Logic & eBay Listing Rules

* **Compact Sequential IDs**: Master catalog uses `ID1001`, `ID1002`, ... to bypass eBay's 50-character Custom Label SKU limits. IDs are allocated inside a single `BEGIN IMMEDIATE` transaction; never split the lookup and the insert across connections.
* **Bin Location Encoding**: SortSwift remarks are encoded into eBay Custom Labels as `ID1001-Bin_A12`.
* **Runtime settings are the source of truth**: pricing tiers (`pricing_rules`) and listing behaviour (`single_threshold`, `group_by_set`, `variation_title_template`, `category_id` in `listing_settings`) are user-editable and persisted in SQLite. Never hardcode these values in prose or logic; read them via `db.get_listing_setting` / `db.get_pricing_rules`. If documentation disagrees with the configured rules, **fix the documentation**.
* **Multi-Item Variation Listings**: When `group_by_set` is enabled, group cards below `single_threshold` by Set Name **and Condition** into multi-item variation listings (see the grouping-key note below).
* **Single Listings**: Cards at or above `single_threshold` are listed as individual singles, as is every card when `group_by_set` is disabled.
* **eBay 80-Character Title Limit**: Variation titles default to `{set_name}: Pick Your Card - {condition} - Complete Your Set`. When a title is too long, trim the **set name**; never abbreviate or alter the condition, which is a factual claim about the cards.
* **Pass source values through; do not re-map them.** Condition (and comparable fields) are taken verbatim from the input export. There is deliberately no `CONDITION_MAP`: the data comes from SortSwift and goes to eBay or back to SortSwift, so a table of our own is a third vocabulary that can disagree with both. A row missing either the `Condition` string or a numeric `ConditionID` is **skipped with a WARN** rather than having a value guessed for it.
* **SortSwift has two exports and Module A needs the eBay one.** `export_eBay_<date>.csv` carries the File Exchange columns — `*Action`, `*Category`, `*Title`, `*ConditionID`, `CD:Card Condition - (ID: 40001)`, the `*C:` item specifics, `PostalCode` and the policy names. `export_SortSwift_<date>.csv` is the inventory export and carries none of them; its price columns are `Your Price` / `Platform Price (…)`. Uploading the wrong one used to skip every row for the same reason — 426 identical warnings on a real file, with the actual cause stated nowhere. `process_batch_csv` now refuses it up front, keyed on the absence of a ConditionID column in any spelling, and names the file to use. Do **not** default the missing `ConditionID` to `4000` to make that file work: it is the right value for an ungraded card, but the same export is also missing category, title, game, postal code and policies, so accepting it trades one loud failure for a listing file that is quietly wrong in five other ways.
* **Repeated per-row warnings are sampled, not repeated.** `_warn_once` logs the first `WARN_SAMPLE_LIMIT` of each kind and `_flush_warn_tallies` reports the rest as a count. Several hundred identical lines bury the summary that says what actually happened, which is how a wrong-export upload came to look like a mystery rather than a one-line fix.
* **Parse third-party CSVs through `tcg_engine.csvtools`**: use `find_column`, `read_csv_text` and `decode_csv_bytes` rather than re-implementing them. Every module previously carried its own column lookup, so a UTF-8 BOM on an eBay report corrupted the first header (`Item number`) and Module B silently recorded every item number as "UNKNOWN" while appearing to succeed. Column matching must stay tolerant of case, whitespace, a BOM and eBay's leading asterisk on required fields.
* **Writing an inventory item group is a full replace, and a partial write is destructive.** A SKU absent from `variantSKUs` is a card taken off the live listing, immediately, with no staged state to inspect and nothing that fails. Any code that writes a group must send **every variation the listing should keep** -- not just the ones it is changing. `refresh_listing` was built this way; `_push_group` was not, and approving a single card's quantity change replaced a 35-card listing with a 1-card listing on a live store. The whole test suite passed while it did so. When touching a group write, the question to answer first is "what is in the listing that I am not sending?"

* **Putting a card back in a group does not put it back on sale.** Removing a SKU from `variantSKUs` takes it off sale, but adding it again is not the mirror image: a withdrawn offer keeps its quantity, price and pictures and its status stays `UNPUBLISHED` until something calls `publishOfferByInventoryItemGroup`. This is reachable with nothing going wrong -- ending a card withdraws its offer, and restocking it later produces an *update*, which never publishes -- and it is invisible from the outside, because eBay hides a variation with no stock from the dropdown, so a complete listing shows one buyable card. `refresh_listing` publishes the group for exactly this reason; `_push_group` deliberately does not, because publishing is all-or-nothing and one invalid card would start failing pushes that work today.

* **Three states look identical from outside a listing and need different remedies:** not in the group (Refresh fixes it), in the group but the offer is unpublished (needs a publish), and in the group with a live offer at quantity zero (needs stock). Diagnose which one before writing anything, and never report an unreadable answer as any of the three -- `scripts/inspect_listing.py` scored every card it failed to read as healthy and declared a broken 123-card listing sound.
* **A File Exchange upload identifies a listing by `ItemID`**, not `Item Number`. The latter is the Active Listings *report*'s name for the same value; using it in an upload leaves the row with no identifier. Revising `PicURL` **replaces** the listing's whole picture set rather than adding to it.
* **Nothing is ever written back to SortSwift.** The deduction file, the orders-CSV upload that produced it and the CLI subcommand behind it were all removed: eBay's orders API is the only thing that deducts stock, and it deducts from our catalogue alone. Do not reintroduce an export aimed at SortSwift, as a convenience or as a fallback. Its numbers drifting upward from reality is expected and is why our catalogue is authoritative. (Stock still clamps at 0, so over-deducting floors rather than erroring.)
* **Seller requirements**: an `Add` needs an item location or eBay returns error 10009. Emit `PostalCode` and **never** `Location` -- they are alternatives and sending both causes that same error. Business policy names (`ShippingProfileName`, `ReturnProfileName`, `PaymentProfileName`) are matched case-sensitively by eBay and are passed through verbatim; a column is omitted entirely when its setting is blank.
* **Item specifics are forwarded, not reconstructed**: any `C:`/`*C:` column in the uploaded export is persisted with the card (the asterisk is a template annotation, strip it) and sent as the inventory item's **aspects**, where eBay wants unprefixed names mapping to *lists* of values. Every SKU in a variation group gets the same aspects, so a field that varies per card is expressed by the variation axis instead, not as an aspect. `Game` is required by eBay and its `default_game` setting **overrides** the export, because eBay only accepts values from its own per-category list while SortSwift exports a looser label. Specifics absent as `C:` columns are derived from the plain SortSwift columns (Set, Name, Card Number, Language, Rarity, Printing).
* **Condition Descriptors**: card listings require a `CD:40001` value for ungraded cards. `ConditionID` stays `4000` for every ungraded card regardless of grade; the grade is carried only by the descriptor. Value IDs differ by card family (game/CCG vs sports `261328`) and are selected from `category_id`. This mapping is the sanctioned exception to the pass-through rule, because eBay's four-value enum is not something SortSwift supplies. An explicit `CD:40001` column in the input still wins.
* **Per-variation images must name their option**: a child row's `PicURL` is `<option name>=<url>`. A bare URL is silently ignored by eBay. Only one variation attribute may carry photos. Because `=` is that delimiter, it is stripped from option names alongside `;` and `|`.
* **Variation options are sorted by card number**, numerically (4 before 16 before 133) with prefixes like `TG12` handled, and the parent's option list must stay in the same order as the child rows.
* **eBay variation syntax**: within one attribute, values are separated by `;`; a `|` starts a *different* attribute. The parent row leaves `Relationship` **empty**; only child rows are marked `Variation`.
* **Variation grouping key is (set, condition)**: eBay applies one ConditionID per listing, so a set holding both NM and LP cards must produce two listings.
* **Anything interpolated into `innerHTML` goes through `escapeHtml`.** Card names, set names and bin notes come from an uploaded CSV; usernames and emails come from a Google display name the account holder controls. Both are rendered to *other* users, so an unescaped cell is cross-user XSS, not self-XSS. Do not escape in `logToTerminal` calls, `alert` or `innerText` -- the first escapes internally and the others are not HTML sinks, so escaping there shows literal `&lt;`.
* **State fields that the UI renders back must be closed sets.** `status` and `role` are Pydantic `Literal`s. A free string is stored verbatim, compared against `"active"` on every request, and rendered into the admin table -- so one bad value both locks the account out and becomes an injection sink.
* **Never hand an exception string to an unauthenticated caller.** `/api/health` logs the detail server-side and returns only a status; a SQLite error discloses absolute paths.
* **Formula-guard only the human-facing export.** `_csv_safe` prefixes cells starting `=`/`+`/`-`/`@` for `/api/export/manifest`, which is opened in a spreadsheet. That is now the only CSV this application writes, and it is the only place the guard belongs: never apply it to anything a machine parses as data, where an apostrophe corrupts a title or a price.
* **Renaming or removing an element id is a deploy hazard.** A browser holding a cached `index.html` pairs old markup with the new `app.js`, and the failure surfaces as `Cannot read properties of null (reading 'classList')` far from the cause. `GET /` is therefore sent `no-store` and `app.js`/`style.css` URLs carry a content hash, so the HTML and the script it names always match. In `updateAuthUI`, fetch elements with `requireElement(id)` rather than `getElementById`, so a stale page names the missing element and tells the user to hard-reload.
* **A long-running module shows its own busy overlay, cleared in a `finally`.** Use `setModuleBusy(key, title, detail)` / `clearModuleBusy(key)` with keys `Batch`/`Sync`/`Orders`. Clearing anywhere other than a `finally` leaves the card locked forever on an early return or a thrown error -- `handleBatchUpload` returns early on the duplicate-file path, so this is not hypothetical. Keep progress bars indeterminate: the server reports no progress and a percentage would be invented.
* **Bulk work goes inside `db.session()`.** Opening and closing a connection per operation costs ~10 ms, so a few thousand card rows spend minutes on setup alone; the session holds one connection open and is a 6x speedup with unchanged commit semantics. It is thread-local because `Database` is a shared singleton in the web app. Also never read an unchanging table inside a per-row loop -- load pricing rules once and use the pure `apply_pricing_rules`.
* **Never do the pipelines' synchronous work inline in an `async def` endpoint.** Use `run_in_threadpool`: inline, it blocks uvicorn's event loop and freezes the whole dashboard rather than just that request, which reads to the user as a hang.
* **A File Exchange `Success` does not mean the change was applied.** Renaming a variation's `CustomLabel` returns Success and silently does nothing; confirmed by re-downloading the Active Listings report. Always verify against a fresh report before building on a result.
* **The same value lives in different report columns depending on the row.** A variation child row carries `Start price` with `Current price` empty; the parent row is the reverse. Use `find_column(..., skip_blank=True)` for those lookups, and never for `Custom label (SKU)` -- a blank there is how the parent row is identified.
* **A variation Revise that mentions `Relationship`/`RelationshipDetails` must include the parent container row** declaring the full `;`-separated option list, with `Relationship` empty and `Quantity` blank on that row. Child rows alone fail with `21916664` plus a misleading `21916639` about pictures: eBay derives the specific set from what you sent, and without the parent that set does not account for the listing's per-variation picture mappings. Confirmed against a live listing. Take the option values from the Active Listings report, never from regenerating them -- the title template may have changed since the listing was created.
* **Never zero a listing off the back of a file that did not parse cleanly.** Every `skipped_count += 1` in `process_batch_csv` happens before the row reaches `file_totals`, so a skipped row looks exactly like a card the dump omitted -- and the remedy for an omitted card is a Quantity=0 Revise row. With every row skipped, `file_totals` is empty and the whole store gets delisted from a file that listed all of it. Reconciliation therefore requires `skipped_count == 0`. If you add a new skip path, this invariant is what keeps it safe.
* **A Revise row is only written when it would change something.** Suppression compares against `last_known_qty` and `last_known_price` -- what eBay is *known* to hold -- and treats every unknown as a change. Never suppress based on `pending_qty`, or a change generated but never uploaded would vanish from all later files. Because `last_known_price` comes from Module B's `Current price` column, nothing is suppressed until a sync has run, which is the correct conservative default.
* **Only Module B may write `ebay_variations.last_known_qty`.** That column means "what eBay reports". Module A records its intent in `pending_qty` instead and must never write `last_known_qty`: generating a CSV is not evidence it was uploaded, and writing it there made the dashboard claim eBay was updated while hiding the drift the two columns exist to show. `upsert_variation` is Module B's call and clears `pending_qty`, since a report from eBay supersedes any outstanding request. Module B also zeroes linked cards absent from the report -- they are not live any more.
* **"Cards" and "copies" are different units.** `total_cards`/`active_listings` count kinds of card; `total_on_hand`/`total_stock` sum physical copies. Label every figure with which it is, and keep the count and sum of the same set filtered identically -- otherwise the ribbon shows copies belonging to cards it is not counting.
* **Batch quantities default to *replace*, not add.** `process_batch_csv(quantity_mode=...)` takes `"set"` (a full inventory dump; the file's total replaces what is stored) or `"add"` (a scan delta). `"set"` is the default because SortSwift's inventory export is a full dump, and the additive reading added the whole inventory to itself on every upload -- a real overselling bug. Never change the default without saying so loudly. Batches are still fingerprinted in `processed_batches` so a duplicate upload is surfaced, though in `"set"` mode a repeat is harmless.
* **In `"set"` mode, rows for one card sum before replacing.** A card in two bins is two rows with one identity, so build a per-file total keyed by `manifest_id` and emit exactly one Revise row per card. Two rows would carry `CustomLabel`s differing by bin, and only one exists on the listing.
* **A Revise row's `CustomLabel` must be the label eBay knows**, read from `ebay_variations.custom_label`, which Module B fills in from eBay's Active Listings report. Do not rebuild it from a card's identity: the bin/remark suffix is not part of the identity and cannot be recovered. Leave `Price` blank on a zero-out row so the listed price is untouched.

* **Backup and restore stay administrative**, because they act on whole database files -- including other accounts' -- rather than on anything the caller owns. Enforce it on the endpoint, not just by hiding the control. (The inventory itself is *not* shared; see §5.)
* **Market prices come from TCGCSV, joined on `(tcgplayer_id, printing)`.** Never on the product id alone -- Normal and Reverse Holofoil differ several-fold and the mistake underprices silently. Their limits are hard: gate every refresh on `last-updated.txt`, send a custom User-Agent, space requests 100 ms, and stay far below 10,000/24h or the application may be banned. A missing or failed price is *unknown*, never `0`, because the rules multiply against it. Keep every value in `price_history`.
* **`build_reprice_csv` carries no `Quantity` column.** A reprice must not touch stock, and an absent column is how File Exchange is told to leave a field alone. Emit only rows whose price differs from `last_known_price`, and use the stored `custom_label`.
* **A grade discount is policy, not data.** The obtainable market price is product-level -- TCGplayer's public data has no per-condition pricing and neither did the SortSwift export relaying it -- so `condition_multipliers` is a configurable table, per-user like the pricing rules. Apply it *before* the tiers via `apply_condition_multiplier`, so a played card lands in a cheaper band. Never default an unrecognised grade to 1.0: return None and report it, because quietly pricing a slab as mint looks normal and is wrong.
* **Pricing rules and listing settings *are* per-user.** Both tables carry a `user_id`, and `SHARED_SCOPE = 0` is the baseline a user inherits until their first save. Never add a query against either table that omits the scope: an unscoped `DELETE` or `SELECT` silently mixes every user's rules together. Thread the caller's `user["id"]` from the endpoint down through `process_batch_csv`; the engine's default of `SHARED_SCOPE` exists for the command line, which has no signed-in user, and is the wrong thing for a request. Pricing rules resolve all-or-nothing, listing settings merge key by key -- see the README for why.
* **The Feed API's Active Inventory report is XML, and its variations are nested.** `LMS_ACTIVE_INVENTORY_REPORT` returns an eBay XML document, not a CSV. Reading it as CSV does not fail -- every line becomes a row, none carries a SKU column, and the sync then looks exactly like a store that ended every listing, so the delisting sweep zeroes the whole mirror. Inside it, a multi-variation listing reports quantity and price **per variation, nested in the item's block**, and the item level carries a blank SKU -- the same convention the Seller Hub report uses to mark a parent row. Reading only the direct children of `SKUDetails` yields one blank-SKU row per listing and matches nothing. Verified against a real store: 4 variation listings holding 62 cards plus 50 unmanaged singles produce 112 records, where the Seller Hub report produces 116 for the same store because it emits parent rows *as well as* children. Match element names loosely and by local name -- the merchant-data schema spells the price `StartPrice` in some places and `Price` in others, and pinning one spelling is how a schema revision becomes a silent zero-match parse. `report_outline` prints a report's element paths with no values, which is the fastest way to settle a shape question.
* **`bulkMigrateListing` needs an item-level SKU on a variation listing, not just one per variation.** eBay answers `400` with `errorId 25002`, "A user error has occurred. The listing SKU cannot be null or empty", for a multi-variation listing whose *listing-level* SKU is empty -- even when every variation carries its own. Every File Exchange variation listing in this store is that shape, and the note above says why: the Active Inventory report shows "a blank SKU at the item level" because that is the parent-row convention. The remedy is a File Exchange Revise carrying only `Action,ItemID,CustomLabel`, which a one-off script emitted (deleted after the migration finished; see commit 6ae59bf); the label is `push.inventory_group_key` of the "<set>|<condition>" group key, so it is deterministic, unique and impossible to mistake for a manifest id holding a variation's SKU. Do not add variation columns to that file -- the fields present are the fields revised, and the parent-row rule below exists because a malformed variation Revise can damage the option list. eBay's other three migration preconditions are invisible from here and produce the same bare 400: fixed-price only, Business Policies rather than the legacy per-listing shipping/return/payment fields, and immediate payment enabled on the payment policy.
* **A refusal is not always shaped like `{"errors": [...]}`, and discarding the body costs a live attempt.** `ApiError` originally appended detail only when it had parsed that shape, so the 25002 above arrived as "returned 400" and nothing else -- indistinguishable from a malformed request of our own, which is the first thing to rule out before retrying something irreversible. The body is now carried on the exception and included in `str()` when no errors parsed. Note the real payload there was a *per-listing* `responses` array inside an HTTP 400 envelope, so a bulk call can fail at both levels at once.
* **A File Exchange Revise re-validates the whole listing, so an old policy violation blocks an unrelated field change.** Setting only `Action,ItemID,CustomLabel` on four listings -- no picture column present at all -- was refused on two of them with `21919137`, "The resolution for provided picture(s) does not meet eBay's Picture Policy requirements ... at least 500 pixels on the longest side". The offending images were already on the listings and had been accepted years earlier; eBay now rejects them on any revise. Useful trick: the dimensions are base64 in the EPS URL's path segment, so `MTM0WDM3NQ==` decodes to `134X375` and names the problem without opening the picture. The consequence for migration is that a listing carrying a below-minimum picture cannot be given the item-level SKU it needs, so the picture has to be replaced first -- and the same error will meet any other Revise aimed at those listings.
* **Every Revise against this store warns `21919456`, "Seller has opted into business policies. Please use policy IDs rather than legacy fields".** It is a warning, not a failure, and it appears even on a file that mentions no shipping, payment or return field whatsoever -- so it describes the *listing's* state, not the file's. Treat it as evidence that the listing may still carry the legacy per-listing fields, which is one of `bulkMigrateListing`'s four preconditions and produces a bare 400 when unmet. Note the warning's own threat: revising such a listing may cause eBay to create new business policies on the seller's behalf.
* **`getOffers` nests the listing id; `publishOffer` and `bulkMigrateListing` do not.** It lives at `offer.listing.listingId`, so reading `offer["listingId"]` on a getOffers result returns "" for a perfectly healthy published offer -- which reads as "this offer belongs to no listing" and is indistinguishable from a real fault. It reported the first successful migration as a failure, and left a safety check comparing every offer against "". Use `inventory.offer_listing_id(offer)`, which reads the nested value and falls back to the top level; do not re-derive it at a call site, because the mistake is silent and the sites are far apart.
* **On migration, the listing-level SKU becomes the `inventoryItemGroupKey`.** Confirmed: a listing given the item-level custom label `SWSH08-FUSION-STRIKE-NM-D9E991EB` migrated into an inventory item group of exactly that name. So the label chosen in `--sku-fix` is not throwaway -- it becomes the permanent key the group is addressed by, which is why it is `push.inventory_group_key` of the group key rather than anything arbitrary.
* **A Google Images search thumbnail is not a usable cover photo, and it silently blocks every later revise.** Two listings could not be given the item-level SKU migration requires, refused with `21919137`. The culprit was not a card scan -- every one of those is around 1550x2100 -- but the **cover photo**, set to an `encrypted-tbn0.gstatic.com/images?q=tbn:...` URL of 308x164. Those thumbnails are always a few hundred pixels and the URLs are not stable links either. `scripts/check_images.py --listing <item id>`, or `--all`, reads the pixel size of every image we hold for a listing from its header alone, without Pillow and without fetching whole files, and is the fastest way to find one; eBay names the offending URL but only its own `i.ebayimg.com` copy, which cannot be matched back to a source. Remember the two sources need different remedies: a cover photo lives in `ebay_listing_overrides` and is changed on the eBay Listings tab, while a card image comes from the export's `CDN Image` column -- or, for an unscanned card, its `Stock Image` column -- and needs SortSwift corrected and the export re-uploaded. Since the fallback exists, the check measures whichever of the two is actually being sent and labels a stock photo as such; a generic catalogue photo can be undersized and block a revise exactly as a scan can. Fixing it on eBay alone is temporary, because the next push or Refresh sends ours back.
* **The order poller is the only thing that deducts a sale, and it must be exactly-once.** Module A used to do it as a side effect -- a card live on eBay and absent from a full inventory dump had gone -- and that inference died when uploads became deltas. The poller re-reads a 30-minute overlap on purpose, because clock skew is real and a missed sale is *invisible*: nothing in the system notices an order it never read. Double-counting is prevented instead by `mark_order_line_deducted`, an UPDATE guarded on `deducted_at IS NULL` that claims `(order_id, line_item_id)` **before** any stock moves -- in the database, never in the poller's memory, so two pollers or a restart mid-poll cannot both deduct. Never replace that guard with a remembered set of what was read. And note the first poll **adopts**: with no watermark eBay hands over 90 days of already-counted history, so it is recorded as handled with a deducted quantity of zero and nothing is removed.
* **`getOrders` carries a buyer's name, address, email and phone, and none of it may be persisted.** This is the account-deletion exemption, not a preference. `app/ebay_orders.py` projects each order down to six named fields and is written as a **keep-list**, never as a copy-then-delete: a delete-list silently admits whatever eBay adds in a later API version. `order_sync._validate` then refuses any line whose keys are not exactly those six, so a mistake fails at the boundary rather than reaching SQLite. When adding a field, expect to change the frozenset, the projection and two tests -- that friction is deliberate.
* **Never zero the store mirror from a report that matched nothing.** The delisting sweep in `sync_active_listings_csv` is gated on at least one row having synced. A report whose columns are not understood still parses cleanly, and "no row matched" is indistinguishable from "eBay ended every listing" -- one of which delists a live store. This is the same invariant `process_batch_csv` enforces with `skipped_count == 0`. It was added after an unrecognised report set all 62 linked cards to 0.
* **An approved plan generates the eBay files; Module A's own download predates every draft edit.** `tcg_engine/plan_exports.py` builds the Add and Revise files from the plan, and it is what makes the drafts page the funnel rather than a parallel view. Two rules hold it together. The plan's `group_key` is **honoured, not recomputed** -- moving a card between listings is one of the three edits the page offers, and re-deriving the grouping from prices and settings would silently discard it and emit a file disagreeing with the screen that was approved. And the Add rows come from `build_add_rows`, the same builder Module A uses; it was extracted for this rather than copied, because a second copy would drift in the rules that are hardest to get right and least visible when wrong -- the parent row leaving `Relationship` empty, the option list matching the child order, and a per-variation `PicURL` naming its option.
* **A cover photo has two destinations, and only one of them is a Revise.** `get_plan_cover_revisions` deliberately restricts itself to groups that map onto a live listing, because a cover cannot be revised onto a listing that does not exist. That leaves the other half to `build_plan_exports`, which reads `get_plan_group_covers` and passes it to `build_add_rows` as the parent row's `PicURL`. Implement one without the other and a staged cover vanishes without a trace: the Add file simply falls back to the first card's picture, and there is no error, no warning and nothing on screen to say a choice was made and dropped -- it shipped that way once. Note that `build_add_rows` takes both `cover_images` (per listing, from the drafts page) and `cover_image_url` (account-wide, from Listing Rules), in that order of precedence; the children keep their own pictures either way.
* **A card with no persisted item specifics cannot be listed, and that is a blocker, not a warning.** eBay marks around twenty specifics required on a card listing, and about thirteen of them -- Card Type, Manufacturer, Graded, Card Size, Character, Stage, both Country fields, Age Level, Year Manufactured, Autographed, Material, Attribute -- exist nowhere but the eBay export. `plan_exports.DERIVED_PLAN_SPECIFICS` fills the five a card's own record can supply (Set, Card Name, Card Number, Language, Finish) and is a floor, not a substitute, which is why `plans.validate_card` blocks the approval instead. Do not soften it into a warning: the Add file builds, looks plausible, and creates hundreds of listings missing fields eBay demands. The only remedy is re-uploading `export_eBay_<date>.csv`, so the blocker names that file.
* **The Condition Descriptor's *style* belongs to export time, not to cataloguing time.** `condition_descriptor_style` chooses between `"Near mint or better - (ID: 400010)"` and the bare `"400010"`, and exists because reports differ on which eBay accepts. A descriptor the upload itself supplied is passed through untouched and marked `condition_descriptor_from_export`; one we rendered is re-rendered at export time from the current setting. Without that flag the style in force the day a card was catalogued is frozen into every future file, and changing the setting appears to do nothing.
* **`manifest.ebay_fields_json` exists because a plan has to rebuild an Add row.** The `C:` item specifics, `ConditionID`, the Condition Descriptor and the back/stock image URLs come verbatim from the eBay export and cannot be derived from a card's identity. They used to be read off the uploaded CSV row, used in memory and discarded -- which meant only the original upload could produce a listing file, so a draft's edits could never reach eBay. Stored as one JSON blob rather than a column each: it is opaque pass-through data, never queried or filtered on, and eBay's templates gain and lose fields, so a column per field would mean a migration every time the export changes shape. Writes **merge**, because a later batch may omit a column an earlier one supplied and dropping a known item specific would quietly degrade the listing.
* **Never persist an eBay user's personal data.** No buyer name, address, email, phone or eBay username may enter either database. This is not a preference: eBay disables a keyset until the developer either receives marketplace account-deletion notifications or holds an exemption, and the exemption is available only to applications that do not persist eBay data. Today the claim is true by construction -- `orders.py` reads an order export in memory and stores nothing from it, and the store mirror holds only our own listings' item numbers, labels, quantities and prices. Deducting stock needs `(order_id, line_item_id, sku, quantity, timestamp)` and nothing more; the buyer is never required, because shipping happens through eBay's own interface. A future `orders` table that quietly acquires a `buyer_name` column would put the account out of compliance with nothing to warn anybody. For the same reason `/api/ebay/notifications` logs a notification's **topic only** -- an account-deletion payload carries the closing user's username and id, so logging it verbatim would create a durable record of precisely the data being disclaimed.
* **The notification endpoint URL comes from configuration, never from the request.** `EBAY_NOTIFICATION_ENDPOINT` must be the public URL exactly as entered in eBay's console, because the challenge response hashes that string. Behind the DSM reverse proxy the URL this process sees is not the URL eBay called, and a mismatch -- even a trailing slash -- fails endpoint validation with an error that never says why. It is the commonest cause of that failure.
* **Both databases run in WAL mode.** Never copy a `.db` file directly to snapshot it -- recent commits may still be in a `-wal` sidecar. Use `VACUUM INTO`, which checkpoints into a single self-contained file.

## 4. 🔐 Authentication Constraints

* **Google Sign-In is the only mechanism.** Do not reintroduce local password login, a registration form, or an auth-disabled development mode, even as a testing convenience. Tests stub `verify_google_id_token` instead.
* **`GOOGLE_CLIENT_ID` is required configuration.** The app must fail fast at startup without it rather than booting into an unusable state, and the ID token audience check must always run.
* **Never ship a default signing secret.** `JWT_SECRET` comes from the environment, or is randomly generated and persisted to the data volume.
* **Google rejects raw-IP and plain-HTTP OAuth origins** (only `localhost` is exempt), so the NAS deployment requires an HTTPS hostname in front of the container. Keep this constraint documented in the README.

## 5. 👤 Data Ownership: Everything Is Per-User

* **Every feature is per-user. Only *defaults* are shared.** A user's cards,
  quantities, bins, stock targets, eBay listing mirror, orders, plans, logs,
  pricing rules and settings belong to that account alone. The only things
  that may be shared are the **factory defaults** a new account starts from
  (the seeded pricing tiers, the default stock-depth target, the seeded
  listing-settings baseline at `SHARED_SCOPE`) and **caches of third-party
  reference data** that are identical for everybody, such as the TCGCSV set
  index. Nothing a user creates or accumulates is ever shared.
* **Apply this to new work without being asked.** When adding a table, a
  column, an endpoint or a background job, scope it to the owning account from
  the outset. Do not ship a shared version intending to scope it later.
* **Do not argue that something "describes the physical collection".** That
  reasoning was used to justify keeping a card's bin and its stock target
  shared across accounts, and it was overruled: another user's shelf is not
  this user's shelf. If two accounts could ever disagree about a value, it is
  per-user.
* **Isolation is structural, not a `WHERE` clause.** Each account's inventory
  lives in **its own SQLite file** (`data/inventory.db` for the deployment
  owner, `data/inventory-user-<id>.db` for everyone else), resolved through
  the registry in `app/main.py`. This was chosen over adding `user_id` to
  sixty-four query methods precisely because the failure modes differ in
  kind: a forgotten scope filter silently shows one account another's cards,
  or pushes them to the wrong eBay store, whereas a mis-resolved database is
  loud and harmless. Never reintroduce cross-account queries -- there is no
  legitimate view that spans accounts.
* **The owner's file keeps its name.** `data/inventory.db` is the deployment
  owner's database and must not be renamed or rebuilt: it holds the live
  catalogue whose `manifest_id`s are the SKUs of live eBay listings, and a
  variation's SKU cannot be renamed (see §3). Migrations touching ownership
  must be additive and lossless.
* **Background jobs act as the owner.** They have no signed-in user, so they
  resolve `user_db.get_owner_user_id()` -- the oldest active admin -- and use
  that account's database, rules **and eBay connection**. A job that fell back
  to a shared baseline would price from rules nobody can see on screen.
* **The eBay connection is per-account.** One application keyset, one refresh
  token per seller: that is how eBay OAuth is designed, so no per-user
  credentials are needed. `get_ebay_client(user_id)` and
  `user_db.get_ebay_token(user_id)` take the account explicitly and have **no
  default on purpose** -- a default here means writing to somebody else's live
  store. The account a consent flow is for comes from the signed OAuth
  `state`, never from a session or a query parameter.
* **Two eBay things are legitimately app-level**: the account-deletion
  notification endpoint, which eBay addresses to the application rather than
  to a seller, and eBay's **call limits**, which are per-application and
  therefore shared across accounts.

## 6. 🧩 Module Layout

* **`app/deps.py` owns the shared runtime.** The databases (`db`, `user_db`),
  the per-account registry (`inventory_for`, `owner_inventory`,
  `inventory_path_for`), the request dependencies (`require_active_user`,
  `require_admin_user`) and the upload guard all live there. It loads `.env`
  itself, before `auth` can read `GOOGLE_CLIENT_ID` at module level, so it
  must be the first `app.*` module imported.
* **`main` re-exports what it uses from `deps`** rather than referencing it
  through the module, because several tests patch `app.main.<name>`. Never
  *redefine* one of those names in `main`: two `Database` instances on one
  file means two connection pools and two per-account caches, so which one
  you get depends on which module you ask, and nothing fails loudly.
  `test_59a_the_shared_runtime_has_exactly_one_instance` pins this.
* **Every route lives in `app/routes/<area>.py`**, one `APIRouter` per area,
  included from `main`. `main` holds **no endpoints at all**: it builds the
  app, sets the security headers, mounts `/static`, includes the routers and
  registers the two background loops. Adding an endpoint means picking the
  router it belongs to, or adding one.

  | Router | What it owns |
  |---|---|
  | `accounts` | Google sign-in, sessions, admin user management |
  | `inventory` | The catalogue, per-card edits, stats, export, Module A upload |
  | `listings` | The eBay mirror, and Module B's reconcile |
  | `pricing` | Tiered rules, condition multipliers, market feed, the repricer |
  | `settings` | Listing rules -- the eBay-facing seller defaults |
  | `plans` | Draft plans, the approval gate, and the push |
  | `orders` | The order poller and the pick list |
  | `ebay` | Consent, connection, seller setup, notifications |
  | `database` | Backup and restore |
  | `system` | The dashboard page, the health probe, the operational log |

* **Extracting or moving a group must not change a single URL.** That is what
  lets the existing tests verify the move rather than being rewritten for it,
  and it is worth more than it sounds: across ten cuts, every test change was
  about *where a name lives*, never about what the code does.
* **Anything a test patches is reached as `deps.<name>(...)` at call time**,
  never imported into a second module. `from app.deps import get_ebay_client`
  gives the importing module its own reference, so a test patching one
  module's leaves the other talking to the real eBay -- an endpoint that keeps
  working while the test believes it is exercising a stub. That is worse than
  a plain failure, because the suite reports success. The eBay library
  functions, the client factory and `get_orders` all follow this rule, and
  their names are deliberately absent from the routers' import lists so a
  second binding cannot come back.
* **A router must not import `main`.** That is the cycle `deps` exists to
  prevent. If a router needs something that currently lives in `main`, move
  it to `deps` or to the router itself, whichever it genuinely belongs to.
* **Background loops register in `main` and live in their router.**
  `APIRouter.on_event` is deprecated, and a loop that silently stops being
  registered is a poller indistinguishable from a shop with no sales. So the
  `@app.on_event("startup")` handler stays beside `app` and does nothing but
  await the router's function.
* **Verify a move by calling the routes, not by reading the route table.**
  FastAPI keeps an included router as one entry, so a naive walk of
  `app.routes` reports served endpoints as missing. A 401 or 422 proves the
  route exists; a 404 proves it was lost.
* **The route walk in `tests/test_deployment.py` must descend into included
  routers.** FastAPI 0.141 keeps an included router as one `_IncludedRouter`
  entry exposing `original_router`, rather than flattening its children into
  `app.routes`. A walk of the top level alone reports a served endpoint as
  missing.
